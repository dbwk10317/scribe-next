# Rocky Linux 기본 빌드와 임시 설치

2026-10-06, Linux x86_64. 검증한 source main은
`5be43ecd5210a52fbc59c12973814d8433d9f601`이며 기본 env_default·비-HDFS·static RPC lane이다.
Rocky userland 컨테이너는 기존 Linux host kernel을 공유한다. Rocky host kernel 자체나
HDFS/shared RPC, RPM 배포와 전체 운영 동등성의 검증으로 확대하지 않는다.

| 환경 | 기본 GCC | Python | 결과 |
| --- | --- | --- | --- |
| Rocky 8.10 | 8.5.0 | 3.12.14 | clean build, 218 tests, DESTDIR, installed help PASS |
| Rocky 9.8 | 11.5.0 | 3.12.14 | clean build, 218 tests, DESTDIR, installed help PASS |

각 실행에서 failure/error/skip은 0이다. Thrift compiler/runtime 0.25.0와 matching fb303,
Boost 1.83 system/filesystem/atomic, 배포판 libevent를 사용했다. component ASan/UBSan 및
HDFS 모의 C API lifetime의 LSan은 전체 suite에 포함된다. 실제 HDFS/JVM 결과는 아니다.

## 정상 준비 조건

RESF가 유지하는 `rockylinux/rockylinux` 이미지를 고정한다. Docker의 옛
`library/rockylinux` 태그는 이번 결과에 사용하지 않았다.

- Rocky 8: `rockylinux/rockylinux@sha256:e8a49c5403b687db05d4d67333fa45808fbe74f36e683cec7abb1f7d0f2338c6`
- Rocky 9: `rockylinux/rockylinux@sha256:8101994123cf3d0a8fee517bee7f39e555c7d92bd2d9eb3303cc988a0eeed00f`

프로젝트 전용 build context에는 다음 공식 공개 archive와 Dockerfile만 둔다.
checkout, 인증 파일과 다른 프로젝트를 context에 넣지 않는다. Dockerfile은 archive
SHA256을 검사한 뒤 의존성을 준비한다. SHA256 검사를 GPG signature 검증이라고 부르지 않는다.

| Source | 공식 위치 | SHA256 |
| --- | --- | --- |
| Thrift 0.25.0 | https://archive.apache.org/dist/thrift/0.25.0/thrift-0.25.0.tar.gz | `66da4707214c54c94bac082103dc67adaf9e08925662700f269170a7b534b214` |
| Boost 1.83.0 | https://archives.boost.io/release/1.83.0/source/boost_1_83_0.tar.bz2 | `6478edfe2f3305127cffe8caf73ea0176c53769f4bf1585be237eb30798c3b8e` |
| Git 2.53.0 | https://www.kernel.org/pub/software/scm/git/git-2.53.0.tar.xz | `5818bd7d80b061bbbdfec8a433d609dc8818a05991f731ffc4a561e2ca18c653` |
| Bison 3.8.2 | https://ftp.gnu.org/gnu/bison/bison-3.8.2.tar.xz (GNU mirror 가능) | `9bba0214ccf7f1079c5d59210045227bcf619519840ebfa80cd3849cff5a5bf2` |

Rocky 8의 기본 Bison 3.0.4는 Thrift의 `--file-prefix-map`을 지원하지 않아 첫 빌드가
실패했다. 공식 Bison 3.8.2를 `/opt/bison-3.8.2`에 준비해 해결했다. Rocky 9는 기본
Bison 3.7.4로 성공했으며 `BUILD_BISON=0`을 사용한다. Bison SHA256은 공개
Homebrew bison formula와 대조했다. GNU signature/keyring 다운로드가 timeout되어
그 signature 검증은 하지 못했다.

배포판 `gcc`만 설치하면 ASan runtime이 빠질 수 있다. 양쪽 첫 suite 실행은
`libasan.so` 누락으로 205 tests, failure 1 / setup error 1이었다. 검증 이미지에
공식 `libasan`·`libubsan` 패키지를 설치한 뒤 새 output으로 전체 218개를 실행해 통과했다.
시험을 skip하거나 sanitizer를 끄지 않았다. DNF 기본 GPG 검사를 유지한다.

고정 upstream object와 Git 보호 옵션은 [Git 준비 안내](linux-build-mvp.md#검증용-git-이력-준비)를
따른다. Stock Git 대신 두 보호 옵션을 지원하는 Git 2.53.0을 준비했다. flags 제거나
자동 fetch fallback을 사용하지 않는다. 이미지 build recipe는
[Dockerfile](../tools/rocky/Dockerfile), sanitizer runtime은
[Dockerfile.validation-runtime](../tools/rocky/Dockerfile.validation-runtime)에 있다.

## 격리된 실행

승인된 Docker 환경에서 context와 출력은 프로젝트 전용 디렉터리를 사용한다.
아래 변수는 이미 준비한 절대경로로 바꾸며 새 output 이름을 사용한다.

```sh
# CONTEXT: public archives + the two Dockerfiles; CHECKOUT: Git checkout
# OUTPUT: existing writable parent outside CHECKOUT
# BASE: the selected pinned RESF digest above; MAJOR: 8 or 9
# BUILD_BISON: 1 for Rocky 8, 0 for Rocky 9

docker build --build-arg BASE="$BASE" --build-arg BUILD_BISON="$BUILD_BISON" \
  -t "scribe-next-rocky-toolchain:$MAJOR" "$CONTEXT"
docker build -f "$CONTEXT/Dockerfile.validation-runtime" \
  --build-arg BASE="scribe-next-rocky-toolchain:$MAJOR" \
  -t "scribe-next-rocky-validation:$MAJOR" "$CONTEXT"
docker run --rm --network none --user "$(id -u):$(id -g)" \
  --cap-drop ALL --security-opt no-new-privileges --cpus 2 --memory 6g --pids-limit 512 \
  --mount "type=bind,src=$CHECKOUT,dst=/validation-input,readonly" \
  --mount "type=bind,src=$OUTPUT,dst=/validation-output" \
  "scribe-next-rocky-validation:$MAJOR" \
  python3.12 -B tools/validate_linux.py --output /validation-output/new-result
```

기존 source export·generated bytes·object freshness·upstream contract 검사를 유지한다.
설치는 새 output의 `stage/` 안으로만 수행한다. source·의존성 compiler·Python·실제 configure
flags·218개 counts·설치 manifest와 logs를 보관한다. `dependency_files`는 prefix 안의
multiarch, `lib64`, `lib` Boost/event 파일을 기록한다. 배포판 libevent 등의 실제 loader
closure는 설치된 바이너리의 `ldd`와 `rpm -qf`/`rpm -qa`로 별도 기록한다.
이 manifest가 시스템 전체 의존성 closure를 대신한다고 주장하지 않는다.

## 근거와 다음 범위

최초 두 정상 실행의 원시 근거는 별도 보관된
`scribe-next-rocky-build-checkpoint-20261006.tar.gz`
(SHA256 `e3588e6a6a678d09223b4cb280fdd81ef5a77e116537e898672df67254def5c8`)에 있다.
각 `validation.json`, `test-results.json`, logs 및 실제 loader library hash와 RPM package
version을 기록한 runtime inventory를 포함한다. 기존 36개 컨테이너 ID 보존도 확인했다.

후속 daemon 전용 개발 RPM의 matching runtime·LICENSE/NOTICE 및 격리 install/remove는
[개발 RPM 안내](rocky-rpm.md)에 기록했다. source 검증을 release·service 배포 승인으로 해석하지 않는다.

후속 manifest 수정도 양쪽 새 source export에서 각각 218 tests/skip 0과 전체 8단계가
통과했다. 기존 manifest에서 빠진 `lib/libboost_system`, `libboost_filesystem`,
`libboost_atomic`의 버전 파일·symlink target hash가 기록됨을 확인했다.
